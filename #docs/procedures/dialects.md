# Procedure: dialects

One plugin, written once, runs on SQLite or on Postgres. One deployment
uses one of them.

## Choosing

`KIT_DIALECT=sqlite|postgres`, else Postgres when `DATABASE_URL` is a
Postgres URL, else SQLite. It is read on the first `table()`, when the
plugins are imported, so the environment is loaded before them
(`node --env-file=.env`). `start()` opens what was chosen:
`{ file }`, `{ dialect: "postgres", url }` or
`{ dialect: "postgres", pglite }`. A database of the other dialect is
refused by name (`MIXED_DIALECT`).

## Tables

`table()`, `column.*`, `index`, `uniqueIndex` and `primaryKey({ columns })`
from `@onetype/stack-api-kit/tables`, never `sqliteTable` or `pgTable`.
Times are `column.timeMs` (bigint on Postgres). A text enum is
`.$type<"a" | "b">()`, checked by the route's schema, not the column. A query is awaited: `.get()`, `.all()` and `.run()` answer on
SQLite only, and `[dialect]` names each one.

## Migrations

`migrations/sqlite/` and `migrations/postgres/`, generated by drizzle-kit
from the same tables, once a dialect, never written twice by hand.
`[migrations]` names a step one folder has and the other lacks. Its
`"public".` prefix is dropped as a step runs.

## What differs, and is handled

A transaction holds one connection; outside it, a pool takes another
client, SQLite and PGlite wait. Claims lock with SKIP LOCKED on Postgres;
migrations and kit tables take an advisory lock.

## Proving it

Tests run on SQLite in memory, and where they reach a store on PGlite
(`KIT_DIALECT=postgres`), with `isolate: false` and `setupFiles:
["@onetype/stack-api-kit/testing/postgres"]`: one PGlite a worker, with
`unaccent`, and a migrated schema a stopped kernel leaves is emptied and
reused. Two connections run against a server, with `KIT_PG_URL`.
