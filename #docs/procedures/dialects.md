# Procedure: dialects

One plugin, written once, runs on SQLite or on Postgres. One deployment
uses one of them.

## Choosing

`KIT_DIALECT=sqlite|postgres`, else Postgres for a Postgres
`DATABASE_URL`, else SQLite, read on the first `table()`: load the
environment before the plugins (`node --env-file=.env`). `start()` opens
`{ file }`, `{ dialect: "postgres", url }` or `{ dialect: "postgres",
pglite }`; another dialect is refused (`MIXED_DIALECT`).

## Tables

`table()`, `column.*`, `index`, `uniqueIndex` and `primaryKey({ columns })`
from `@onetype/stack-api-kit/tables`, never `sqliteTable` or `pgTable`.
Times are `column.timeMs` (bigint on Postgres). A `count`, `sum` or
`max` of a bigint reads as text from node-postgres: `.mapWith(Number)`.
A text enum is `.$type<"a" | "b">()`, checked by the route's schema. A
query is awaited; `.get()`, `.all()` and `.run()` are SQLite's, and
`[dialect]` names each.

## Migrations

`migrations/sqlite/` and `migrations/postgres/`, generated by drizzle-kit
from the same tables, once a dialect, never written twice by hand.
`[migrations]` names a step one folder has and the other lacks. Its
`"public".` prefix is dropped as a step runs.

## What differs, and is handled

A transaction holds one connection; outside it, a pool takes another
client, SQLite and PGlite wait. Claims lock with SKIP LOCKED on Postgres;
migrations and kit tables take an advisory lock.

## Proving it

Tests run on SQLite in memory, and on PGlite (`KIT_DIALECT=postgres`):
`isolate: false`, `setupFiles: ["@onetype/stack-api-kit/testing/postgres",
<yours>]`, yours awaiting `configureTestKernels({ pglite: { extensions } })`
so PGlite starts there. A stopped kernel's schema is reused; shard a large
run (`--shard=1/2`). `KIT_PG_URL` runs what needs a server.
