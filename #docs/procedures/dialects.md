# Procedure: dialects

One plugin, written once, runs on SQLite or on Postgres. One deployment
uses one of them.

## Choosing

`KIT_DIALECT=sqlite|postgres`, else Postgres when `DATABASE_URL` is a
Postgres URL, else SQLite. It is read on the first `table()`, when the
plugins are imported, so the environment is loaded before them
(`node --env-file=.env`). `start()` opens what was chosen:
`{ file }`, `{ dialect: "postgres", url }` or
`{ dialect: "postgres", pglite }`. A database of the other dialect is
refused by name (`MIXED_DIALECT`).

## Tables

`table()` and `column.*` from `@onetype/stack-api-kit/tables`, never
`sqliteTable` or `pgTable`. Times are `column.timeMs` (bigint on
Postgres). A query is awaited: `.get()`, `.all()` and `.run()` answer on
SQLite only, and `[dialect]` names each one.

## Migrations

`migrations/sqlite/` and `migrations/postgres/`, generated by drizzle-kit
from the same tables, once a dialect, never written twice by hand.
`[migrations]` names a step one folder has and the other lacks.

## What differs, and is handled

A transaction holds one connection. On a Postgres pool, work outside it
takes another client; on SQLite and PGlite, one connection each, it waits.
Claims lock with SKIP LOCKED on Postgres. Migrations and the kit's own
tables take an advisory lock, so two processes starting together take
turns.

## Proving it

Tests run on SQLite in memory. Where a suite reaches a store, it also runs
on PGlite (`KIT_DIALECT=postgres`), a schema per test kernel. What only
two connections show runs against a server, with `KIT_PG_URL` set.
